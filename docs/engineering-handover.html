governance-provisioning-service

A durable, async provisioning queue over the governance connector framework. This document is derived from a direct read of the source at srallapally/governance-provisioning-service (branch main), not from its planning docs — file references are given throughout so claims can be checked against the code.

01How it works

What does this service actually do?

The service is a claim-based work queue sitting in front of the governance connector framework's per-target facades (create/update/delete/search against an external system such as an HR system, AD, or a SaaS app). Callers enqueue a mutation over HTTP and immediately get back 202 with an operationId; a background dispatcher claims rows from a Postgres-backed table and executes them against the target through the framework, one attempt at a time, at a rate the target's configured concurrency budget allows.

The repository's own README states the boundary precisely: this service owns the claim loop — the durable operation table, the dispatcher, the admission gate, and the HTTP surface. The framework owns executing one operation correctly — attempt deadlines, abort propagation, circuit breakers, connection pooling. Everything in this document is on this service's side of that line; the framework itself is out of scope for this handover.

Four terminal outcomes exist, deliberately distinct because the operational remedy differs per outcome: SUCCEEDED, REJECTED_PRE_DISPATCH (never reached the target — safe to retry wholesale), FAILED_CONFIRMED (target refused — will refuse again until the input changes), INDETERMINATE (deadline expired with no answer — only reconciliation can settle it). This distinction is the organizing idea of the whole codebase; see §6 and §8.

Writes to one object never interleave. Every operation is assigned a lane key — create:<objectClass>:<nameAttrValue> for creates, uid:<objectClass>:<uid> for update/delete/deltas — and the claim query refuses to let two operations on the same lane run concurrently, or let a second one jump ahead while the first's outcome is still unresolved. src/ops/admission.ts (laneKeyFor), src/ops/OperationStore.ts (CLAIM_SQL)

03Operation flow, end to end

What does the flow of a provisioning operation look like?

  1. Request. Caller sends POST /instances/:instanceId/objects/:objectClass (or PUT/DELETE/add-values/remove-values) with a bearer JWT. src/http/objectsRoutes.ts
  2. Auth. requireJwt() validates the token against a JWKS-fetched key, issuer, audience, algorithm allowlist, clock skew, and max age before any route runs — mounted ahead of every router, including status. src/http/auth.ts
  3. Lazy registration. ensureApplication(instanceId) runs for every request against that instance. First time an id is seen, its config is fetched from the ApplicationConfigStore and registered with the connector registry; on later requests this is a cache hit. src/config/registerApplication.ts
  4. Synchronous validation. For CREATE, the route resolves the object class's naming attribute (schema call through a leased connector) and rejects with 400 if the request body doesn't carry it — this is the one piece of validation that happens before the caller's connection is released, because the read-back protocol depends on it existing.
  5. Admission. admitAndEnqueue() reads current PENDING+AWAITING_READBACK depth for (instanceId, priority); over the cap (1,000 interactive / 10,000 batch, by default) → 429 with the observed depth. Otherwise the lane key is computed and the row is inserted. src/ops/admission.ts
  6. Enqueue. Insert is idempotency-key-deduplicated under a transaction-scoped Postgres advisory lock (not a unique index — see §7 for why). Row starts PENDING, attempt_count = 0. OperationStore.enqueue
  7. 202 response. Caller gets { operationId, status: "PENDING", idempotencyKey } immediately. Nothing has run yet.
  8. Claim. On its next tick, the dispatcher's claimBatch query picks up to claimBatchSize (default 100) eligible rows across all registered instances — respecting per-instance/per-priority caps, excluding busy lanes, one row per lane per cycle — and marks them RUNNING under FOR UPDATE SKIP LOCKED. Dispatcher.runCycle → OperationStore.claimBatch
  9. Lease + attempt. The dispatcher acquires a connector lease for the instance and calls the matching facade method (create/update/delete/addAttributeValues/removeAttributeValues) with an attempt deadline. See §5 for the per-op-type resolution logic.
  10. Finalize. The attempt's outcome is written back in one transaction that also inserts the slim operations_history row — a record can never reach terminal status without its permanent counterpart existing. OperationStore.finalize
  11. Poll. Caller polls GET /operations/:operationId for status; this is poll-only — there is no webhook/callback path in this codebase. Falls back to operations_history once the hot row ages out of its partition. src/http/operationsRoutes.ts
Reads (GET .../:uid and the streaming search) never touch the operation table at all — they acquire a lease and call the facade synchronously, in the request. Only the five mutation routes are async.

Every enqueue also carries an Idempotency-Key (client-supplied header, or a server-generated UUID if omitted) and a priority — interactive or batch, defaulting to batch. Priority determines admission cap and claim ordering, not correctness.

05Flow per operation type

What is the flow of each operation?

CREATE — the read-back protocol

This is the one operation type with genuinely special handling, because a create's target-minted uid means a blind retry after a timeout can silently produce a duplicate account.

  1. Attempt facade.create(objectClass, attrs, options) against an attempt deadline.
  2. Success → SUCCEEDED, uid + object persisted.
  3. ALREADY_EXISTS → FAILED_CONFIRMED immediately (confirmed refusal, not retried).
  4. Retryable connector error (before any deadline) → ordinary exponential backoff (§8), up to maxAttempts.
  5. Deadline expired → the target's connector may have applied it. If the connector supports equality search by name, the row moves to AWAITING_READBACK and is parked — releasing its mutation slot and connector lease, but keeping its lane blocked — until attemptDeadlineMs.create + readBackGraceMs has elapsed. If the connector cannot search by name, it goes straight to INDETERMINATE (no way to check).
  6. Once the wait elapses, the dispatcher reclaims the row (still by lane, honoring AWAITING_READBACK as blocking until due) and searches for the object by its naming attribute — it never re-issues the create. Found → SUCCEEDED (viaReadBack: true). Confirmed absent → exactly one requeue for a second attempt; a second miss → INDETERMINATE.

Dispatcher.attemptCreate / resolveCreateAfterDeadline / resumeReadBack

UPDATE

Always a full replace. UNKNOWN_UID → FAILED_CONFIRMED. Any other retryable failure, including a deadline, goes through ordinary backoff — replace semantics make replaying safe, so there is no read-back step here.

DELETE

UNKNOWN_UID is treated as SUCCEEDED (alreadyAbsent: true) — the desired end state, object absent, has been reached. Any other retryable failure backs off and retries; delete is idempotent by the same logic as update.

ADD_VALUES / REMOVE_VALUES

Missing uid → REJECTED_PRE_DISPATCH before dispatch. UNKNOWN_UID → FAILED_CONFIRMED. On a retryable failure, the dispatcher checks the connector's declared idempotentDelta capability: if the manifest doesn't assert the target applies deltas with set semantics, a retry could silently double-apply the grant (a privilege change), so it goes to INDETERMINATE with zero retries instead. Only a connector that explicitly declares idempotent delta semantics gets ordinary backoff here. There is no read-back for deltas — no naming attribute to search on — reconciliation is the only backstop.

07Scaling model

How does it scale?

Horizontally, without coordination

Multiple dispatcher replicas run against the same Postgres table with no leader election and no external lock. The claim query uses FOR UPDATE OF o SKIP LOCKED: two replicas racing the same backlog simply partition it — each takes what the other hasn't already locked. A replica that dies mid-cycle loses only the rows it had claimed (they're picked up by the reaper, §8). This is the entire scale-out story for the dispatcher; there is nothing else to configure to add a replica.

Dispatcher.ts header comment; OperationStore.claimBatch (CLAIM_SQL)

Per-instance concurrency budget

Each connector instance (application) has a mutationConcurrency ceiling (framework-owned, part of its runtime config) that bounds how many attempts against that target can be in flight at once, cluster-wide — enforced by the claim query's per-instance cap, computed fresh every cycle from the dispatcher's own in-memory in-flight count.

Interactive / batch reservation

Within that budget, an interactiveSliceFraction (default 0.2) reserves a slice of mutation slots that batch work may not draw from — interactive work may use the whole budget, batch is capped at budget minus the slice. This is enforced as a hard claim-time cap (batchFree/totalFree in InstanceAvailability), not merely a claim-ordering preference — see BUG-4 in the bug log, where an ordering-only version passed load tests by coincidence but failed under real saturation.

Rate limiting per operation kind

An instance can declare a token-bucket rate limit per op kind (create/update/delete); checked before claiming, not before the attempt, so a rate-limited row isn't claimed and held — it simply isn't offered that cycle.

Admission as the flow-control signal

Rather than an unbounded queue absorbing more work than the drain rate can clear, the enqueue path rejects with 429 once PENDING+AWAITING_READBACK depth for an instance/priority hits its cap, returning the observed depth so the caller can back off deliberately. This check is advisory under concurrency (a small overshoot is accepted as cheaper than serializing every enqueue).

Data layer

The operation table is range-partitioned by day, with a documented 24-hour hot retention window; partitions are created/dropped by an in-process hourly job, not an external cron. This bounds the hot table's size regardless of throughput, keeping the claim query's working set — and its partial index — small and roughly constant. The dispatcher's own Postgres pool is sized independently of any HTTP-layer pool (dispatcherPoolMax, default 5) and carries a statement_timeout.

A soak run against a real Cloud SQL instance is referenced in the README as verifying ~1,168 ops/s sustained, with the config-store read-per-operation cost specifically called out as a hot-path concern worth caching (resolve once per attempt, at claim time; cache by (applicationId, version)).

08Failure and retry

How does it handle failure and retry?

The outcome taxonomy is the retry policy

Rather than one generic "retry on failure," every failure is classified into one of the four terminal outcomes (§6) or a transient REQUEUE/DEFER_READBACK, and the classification is the retry decision:

  • REJECTED_PRE_DISPATCH — nothing happened at the target; safe to resubmit as a fresh operation.
  • FAILED_CONFIRMED — the target explicitly refused; retrying without changing the input will fail again, so the dispatcher doesn't.
  • REQUEUE (non-terminal, internal) — a retryable connector error or an idempotent-operation deadline. Exponential backoff: min(backoffMaxMs, backoffBaseMs × 2^attemptCount), default base 1s / ceiling 60s, up to maxAttempts (default 5), after which it becomes FAILED_CONFIRMED or INDETERMINATE depending on the path. The backoff is enforced by excluding the lane from claiming until the delay elapses — not by an in-process sleep — so it survives a process restart and doesn't hold a connector lease or mutation slot while waiting.
  • INDETERMINATE — genuinely unknown outcome (deadline with no way to check, or backoff exhausted on an unknown-outcome path). This is a deliberate admission that the dispatcher cannot resolve every case; reconciliation against the target is the documented backstop, and is out of scope for this service.

The reaper — recovering a dead dispatcher's claimed rows

A replica that crashes mid-attempt leaves its claimed rows RUNNING forever, invisible to future claim queries (which only look at PENDING). Left unrecovered this also silently breaks partition retention — the drop gate correctly refuses to drop a partition holding any non-terminal row, so one stranded row pins a whole day's partition open (documented as BUG-2 in the framework's history). The dispatcher runs a reaper pass on its own cadence (default every 60s, serialized across replicas via a pg_try_advisory_xact_lock so only one runs a pass at a time): rows RUNNING past a threshold (default 10 minutes — must exceed the longest legitimate attempt) are routed by op type — creates go to AWAITING_READBACK (their outcome is unknown, so read-back applies exactly as it would after a live timeout), everything else (idempotent by construction) returns straight to PENDING. Neither path increments attempt_count — the process died, which isn't the operation's fault.

OperationStore.reapStale; Dispatcher.maybeReap

Graceful shutdown

On SIGTERM/SIGINT: the HTTP server closes first (nothing new can enqueue), then dispatcher.stop({drainBudgetMs}) waits for in-flight attempts up to a bounded budget (default 8s) — deliberately bounded, because the container has nothing above it that will wait indefinitely, and whatever grace period the deployment grants arrives eventually as SIGKILL regardless. A straggling attempt past that budget is simply left RUNNING, to be recovered by the reaper — the same mechanism that handles a hard crash, not a distinct failure mode. A second-stage grace window then polls in-flight count before disposing connector instances, to avoid tearing one down under a genuinely still-running attempt.

Dispatcher.stop; provisioning/wiring.ts (stop)

Known, fixed defects worth knowing about

The in-repo BUG_LOG.md documents three fixed defects, all directly relevant to correctness under failure:

  • BUG-4 (medium) — the interactive/batch reservation was computed but never enforced; a batch flood could starve interactive work. Fixed by making it a hard claim-time cap. The regression test deliberately asserts an interactive op starts before an in-flight batch attempt completes — a latency-percentile comparison alone would not have caught this.
  • BUG-7 (medium) — test sources were excluded from typechecking entirely, so a signature change compiled cleanly in tests while silently passing undefined/NaN through to Postgres at runtime. Fixed with a separate tsconfig.test.json run in CI.
  • BUG-8 (high) — a claim cycle racing stop()'s pool closure threw an unhandled rejection that crashed the whole process outright (not just stranded a row) — only reproduced against real Cloud SQL latency, never against local Postgres. Fixed with a catch clause that degrades this to the ordinary reaper-recoverable case.
All three were found through soak testing against a real network-latency database, not local Postgres or unit tests. Local Postgres's near-zero round-trip latency specifically hid BUG-8 for the whole of P0–P7. Worth keeping in mind for any future change to the claim/stop path: local tests alone did not catch this class of bug once.
